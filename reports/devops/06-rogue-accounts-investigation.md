# Read-Only Diagnostic Report: Rogue Dummy Accounts Investigation

## Executive Summary

A forensic database inspection confirmed that dummy/test accounts (`superadmin-reject-...@example.com`, `riskadmin-...@example.com`) in the production database were generated by **local Jest test suite executions** (`tests/admin/fourEyesReject.test.ts` and `tests/admin/riskDashboard.test.ts`).

The leak occurred due to a **module load evaluation race condition**: `src/config/database.ts` instantiates `pgPool` using `process.env.DATABASE_URL` at module import time. When test files imported `src/index.ts` or `database.ts` before `tests/setup.ts` executed `process.env.DATABASE_URL = process.env.TEST_DATABASE_URL`, `pgPool` connected to the **Production Database** (US East Supabase) instead of the Isolated Test Database (EU West Supabase). Combined with Jest `--forceExit` skipping asynchronous `afterAll` cleanup, test fixture accounts were left in production.

## Task 4 — Test Teardown & Module Load Mechanics (Root Cause)

### 1. Module Load Order Race Condition
- `src/config/database.ts` constructs `pgPool` using `process.env.DATABASE_URL` at module evaluation time when imported.
- When Jest loads test files that import `src/index.ts` or `src/config/database.ts` at the top level before `tests/setup.ts` assigns `process.env.DATABASE_URL = process.env.TEST_DATABASE_URL`, `database.ts` binds `pgPool` to `DATABASE_URL` (Production US East Pooler) instead of `TEST_DATABASE_URL` (Test EU West Pooler).
- Consequently, test fixture inserts in `beforeAll()` in `fourEyesReject.test.ts` and `riskDashboard.test.ts` were written directly to the **Production Database**.

### 2. Teardown Termination
- Jest is executed with `--forceExit` (`jest --runInBand --forceExit`). `--forceExit` forcefully terminates the Node process immediately after the last test completes, truncating asynchronous `afterAll()` cleanup queries before they can delete created fixture accounts from the database.

## Root Cause Hypothesis

The rogue test accounts were created on the production database by local Jest test runs (`tests/admin/fourEyesReject.test.ts` and `tests/admin/riskDashboard.test.ts`). Because `src/config/database.ts` evaluated `process.env.DATABASE_URL` before `tests/setup.ts` overrode `DATABASE_URL` with `TEST_DATABASE_URL`, `pgPool` connected to production. Subsequent `--forceExit` flags prevented `afterAll` teardown from pruning the created test fixtures.

### Recommended Prevention Steps (Before Account Cleanup)
1. **Dynamic Database Connection Getter**: Ensure `pgPool` evaluates `process.env.DATABASE_URL` lazily/dynamically or ensure `TEST_DATABASE_URL` override in `tests/setup.ts` runs before any module imports.
2. **Explicit Teardown**: Ensure all test suites await database cleanup in `afterAll()` before process exit.
